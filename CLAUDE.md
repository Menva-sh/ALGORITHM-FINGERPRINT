# CLAUDE.md — Algorithm Selection via Learned Complexity Fingerprints

## Project goal
Given a graph and a source-target query, predict which shortest-path algorithm will be fastest,
WITHOUT running all of them. Pipeline:

    Graph instance -> Complexity Fingerprint (features) -> ML selector -> Best algorithm

This is a final-year project. Results must be honest, reproducible and backed by experiments.
Never claim a result that has not been measured.

## Our contributions (in priority order)
1. Cost-aware features: features are grouped into cost tiers, and feature-extraction time is
   counted inside the total time. We plot selection quality vs feature cost (Pareto curve).
2. Probing features: run the default algorithm for a tiny budget (k node expansions) and use
   what we observe (frontier growth, queue churn) as extra features.
3. Uncertainty: the selector can say "not sure" (calibrated probabilities / conformal sets)
   and fall back to a safe default or run the top 2.
4. Explainability: SHAP + permutation importance, and distil the forest into a small rule list.
5. Strength checks: train small -> test large, synthetic -> real graphs, op-counts vs wall-clock.
6. Wow layer (only after the above works): Streamlit demo app, 2D "algorithm map" (UMAP),
   real city road network case study (OSMnx), tipping-point analysis.

## Task definition (keep it fixed)
Single-pair shortest path (source s, target t) on a graph with non-negative weights.
All candidates must return the SAME shortest-path cost. If they do not, that is a bug.

Candidate algorithms (all implemented by us on one shared adjacency-list structure,
same language, so the comparison is fair):
- Dijkstra (binary heap)
- Bidirectional Dijkstra
- A* with Euclidean heuristic (ONLY on graphs that have coordinates: grid, random geometric, road)
- BFS and Bidirectional BFS (ONLY on unweighted graphs)
Algorithms that are not applicable to an instance are masked out; the selector only chooses
among applicable ones. DFS is NOT a candidate (it does not find shortest paths).

Do NOT use networkx for timing. networkx is fine for generating graphs and for tests.

## Rules (important)
- Split train/test BY GRAPH (group split), never by row. One graph with many queries must stay
  entirely in train or entirely in test.
- Fixed random seeds everywhere. All settings live in `config.yaml`.
- Timing: use time.perf_counter_ns(), warm-up runs, median of repeated runs, and time ONLY the
  search (not graph building or parsing). Also record operation counts (nodes popped, edges
  relaxed) as a hardware-independent label.
- Ties: if the best two algorithms are within a small threshold (set in config), mark the
  instance as a tie; evaluate with regret, not only accuracy.
- Always report: selection accuracy, regret, and NET time saved
  (net = feature time + inference time + chosen algo time, compared against the best single
  fixed algorithm AND against running all candidates).
- Check class balance of the labels before training. If one algorithm wins >80%, fix the graph
  mix before modelling.
- Never leave results as hardcoded numbers. Every table and plot must be regenerated by a script.
- Write tests with every stage. Do not move to the next stage until tests pass.

## Feature tiers (cost levels)
- Tier-0: free metadata, O(1): |V|, |E|, density, weighted flag, has-coordinates flag.
- Tier-1: one linear scan O(V+E): mean/var/max degree, degree entropy, min/max/mean/std weight.
- Tier-2: sampled estimates: clustering and diameter estimated from random samples / few BFS.
- Tier-3: exact and costly: exact diameter, exact clustering, spectral features.
- Probe features: collected while running a tiny budget of the default algorithm.
Every feature function records its own runtime so we can compute tier costs.

## Graph families to generate
Erdos-Renyi, Barabasi-Albert (scale-free), Watts-Strogatz (small-world), 2D grids (with and
without obstacles), random geometric graphs. Vary size (100 to 5000+ nodes), density, and weight
distribution (unit, uniform, heavy-tailed). Real graphs for testing only: SNAP, Network Repository,
road networks via OSMnx.

## Dependencies
numpy, pandas, scipy, scikit-learn, networkx, shap, umap-learn, matplotlib, pytest, pyyaml,
streamlit, osmnx (optional), mapie or a hand-written conformal routine.
